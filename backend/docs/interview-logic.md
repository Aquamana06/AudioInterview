# インタビューロジック

- interview/agent.py: 抽出、状態更新、質問方針、通常セッションのターン生成
- interview/profile_agent.py: 初回セッションのプロフィール形成
- interview/longitudinal.py: 継続セッション開始文と過去記憶の選択
- db/memory.py: 参加者プロフィール、セッション要約、記憶ノードと関係の保存
- api/routes.py: セッション作成・更新・終了、回答編集時の再構築

LLM が利用できない場合も、定型の質問や抽出フォールバックを使って会話を継続できます。

初回プロフィール面談は、仕事内容や立場を聞くところから始めます。2回回答を受けても今の仕事の経験年数が分からない場合は、「そのお仕事は何年目になりますか？」と必ず確認します。既に本人から年数・月数が示されていれば聞き直しません。経験年数について「答えたくない」「言いたくない」と答えた場合も、その意思を `experience` に記録して確認済みとし、年数や拒否の理由を聞き直しません。拒否の記録は初回をやり直す場合も引き継ぎます。

通常面談へ進むには、初回プロフィール面談で経験年数または回答を希望しない意思が確認でき、`profile.min_turns`（既定7回）以上の回答と `profile.min_covered_fields`（既定5項目）以上の情報がそろい、自動終了する必要があります。この場合だけ状態へ `profile_completed: true` を保存します。手動終了、本人の終了希望、基準未達のまま `profile.max_turns`（既定14回）に達した場合は未完了とし、次回も初回プロフィール面談になります。途中までの会話や記録は保存しますが、それだけでは完了扱いにしません。モードはセッション単位で保存し、再開・回答編集でも維持します。完了判定はアカウントごとです。過去の終了済み件数だけでは完了とせず、この完了記録のない既存アカウントも次回は初回扱いになります。

インタビュー開始時は `load_participant_profile` で長期プロフィール・保存済みドメイン知識・終了済み件数を取得し、過去セッションの要約・記憶ノードは取得しません。継続面談では、冒頭の回答から対象業務を抽出して特定できた時点で、同じアカウントの終了済みセッション全体から同じ業務の履歴を検索します。対象がまだ不明なら検索しません。過去セッションの `messages` は取得せず、セッションID付きの要約・構造化情報・関連記憶を渡します。今回のセッション内の会話履歴は別に保持します。coverage と depth（coverage達成後のanchorを含む）の質問生成で、過去の同じ業務の情報と長期プロフィールを参照します。「以前のインタビューでは〜」の出典は別セッションの情報だけに限定し、今回の発言は「先ほど」と表現します。長期プロフィールは特定セッションの発言ではなく、背景として扱います。

`participant_domain_knowledge` は、本人から教わった現場用語の意味をセッションとは独立して引き出すための用語集です。終了時の要約生成で `domain_knowledge`（term / meaning / scope / evidence_message_ids）を抽出し、今回の本人の回答IDを根拠として持つものだけ保存します。同じ参加者・適用範囲・用語の訂正は上書きし、他の用語は維持します。開始発話、対象業務特定前、coverage、depth、anchor、イレギュラー確認、プロフィール面談の質問生成でも参照します。意味を聞き直さず、未説明の部分や記録と異なる用法だけ必要に応じて確かめます。用語の定義を今回の業務条件として扱わず、状態スコアは更新しません。既に要約生成済みの過去セッションを再処理するバックフィルは行いません。保存に失敗した場合は既存の要約復旧とともに再試行します。

同じ業務の履歴がある場合は、対象業務が分かった直後に、まず今回いつもと違うことがあったかを尋ねます。最初の回答で既に普段どおり／例外の内容が説明されていれば、この確認は繰り返しません。`usual_work` はこの冒頭の確認を省略できるかの判定だけに使い、`task_revisit_work` で確認の重複を防ぎます。冒頭の一問以降は「いつも通り」専用のガイド・過去の事実の選択・FRAM項目の切り替えを行わず、初回と同じ状態に基づく通常の方針を選びます。「いつも通り」だけで過去の情報を今回の事実やスコアに引き継ぎません。

coverage と depth では、同じ業務の過去情報と長期プロフィールを背景として質問生成に渡し、今回の会話も踏まえて同じことを聞き直さず、今の方針で進むよう短く指示します。過去情報の有無でガイドへ別の指示を追加せず、比較の仕方や具体的な確認質問を指定しません。状態更新は今回の回答だけで行います。参照候補は `memory_referenced`、質問生成に渡したかは `guide.past_memory_used` に表示します。

質問生成は、知ったふりをせず相手に教わるトレーニーの姿勢を共有します。用語や前提の確認は、対象業務と今の質問方針を理解するために必要な範囲で行います。保存済みの用語の意味は聞き直さず、今回の説明を優先します。この姿勢は通常面談、初回プロフィール面談、開始発話の生成に適用します。

回答不能・拒否の記録はセッション状態の `unanswered_points` に保持します。抽出器は「分からない」「そこまで考えていない」「答えたくない」とされた点だけを短く記録し、通常面談・プロフィール面談の両方で質問生成へ毎回渡します。会話履歴や既出質問の件数上限でこの記録は消しません。直後の深掘りは中断して別の観点へ進み、後続ターンもcoverage・depthの不足よりこの制約を優先します。同じ質問文を生成した場合は別の定型質問へ差し替えます。言い換えの意味判定用の別モデルや恒久的なNGリストは導入せず、セッション内だけの制御です。本人が後から自発的に話すことは妨げません。「分からない」だけで抵抗のカウントや深さのスコアを増やしません。

通常面談は `ending.max_turns`（既定20回）の回答を受けた時点で、coverage・depth・イレギュラー情報の不足、深掘り中、相手からの逆質問の有無にかかわらず終了します。20回目の回答を保存して終了の挨拶を返し、21回目の送信は終了済みとして受け付けません。プロフィール面談もこの上限を超えず、既存の14回の上限は維持します。上限到達だけではプロフィール完了扱いにしません。

終了判定の最低 `task_coverage` は `0.45`、原則の最低 `irregular_coverage` は `0.6` です。ただし `irregular_coverage` が `0.4` のまま3回答連続した場合は、0.6に達しなくてもイレギュラー情報の終了条件を満たしたとみなします（`ending.partial_irregular_coverage: 0.4`、`ending.partial_irregular_turns: 3`）。最初に0.4になった回答を1回目として、状態の `irregular_partial_turn_count` に連続回数を保存します。スコアが0.4以外になれば0に戻し、0.2の継続は対象にしません。スコアを0.6へ水増しする処理は行わず、task_coverage・depth・高深度の回数など、ほかの終了条件と、相手からの質問・進行中のanchorを先に扱う制御は維持します。この例外にも通常の終了条件にも達しない間は、今回語られた平常時の条件・手順から、予定どおりに進まない場合の状況や対応を一問ずつ尋ねます。この段階では新しいanchorより例外確認を優先し、途中のanchorの質問には回答を受けてから進みます。質問しただけでは加点せず、本人が説明した実際または仮定の例外状況・対応を抽出した場合に加点します。明確な終了意思・手動の終了操作はこの条件によらず優先します。

業務の不足確認では FRAM 各項目のスコアが最も低い項目を一つ選びます（未取得の0を優先し、同点は定義順）。anchor終了後は coverage が0.45未満の場合だけ不足確認へ戻り、達成済みなら通常のdepth・イレギュラー確認へ進みます。例えば `precondition: 0` なら、「事前の行動」「事前の確認」「開始の判断」「他の業務への依存」「他者への依存」「開始の阻害」の6つを切り口の候補として質問生成に渡します。会話に合い、まだ確認していないものを一つだけ選び、既出・回答不能な点は避けます。6項目を順番にすべて聞く台本にはしません。「現場がどんな状態になっている必要があるか」という抽象的な聞き方を避け、生成失敗時は「ダスター交換に取りかかる前に、普段どのようなことをしていますか？」のように事前の行動を尋ねます。抽出でも開始に必要な行動・確認の完了や依存先の準備を前提条件として捉え、単に直前にしていた無関係な行動は含めません。手順・知識・経験など複数の抽象的な観点をまとめて尋ねず、会話で分かっている現場の言葉に合わせます。選んだ項目はログの `guide.fram_focus` に出力します。生成に失敗した場合も、その項目の質問にフォールバックします。

FRAMの意味は `FRAM_MEANINGS` で抽出と質問生成に共有します。質問生成では会話履歴の後に今の方針と選択項目の意味を置き、直前の話題より今回の方針に沿って生成するよう伝えます。停滞時の補足も、今の方針の範囲で既出内容を聞き直さないための指示です。`guide` は生成に渡した方針であり、生成後の質問の意味を検証した結果ではありません。日本語の「か。」「教えてください。」などで終わる質問も、疑問符付きの質問と同様に `asked_points` と質問回数へ記録します。

通常面談の `deep_dive_opportunity` は、選択・優先順位・必要性・重要性・工夫や調整を示す発話に、まだ説明されていない理由や判断基準を尋ねる余地がある場合に検出します。単なる名詞の具体化は検出の目的に含めません。`deep_dive_anchor` には「他のタスクの方が優先」のように、判断を含む短い原文を保持します。

`resource` は作業遂行に必要な道具・設備・人員・知識・情報・経験などを対象とし、材料（原料・食材など）は除外します。材料の種類や一覧を質問せず、材料を挙げただけの回答を `fram_resource` に抽出・加点しません。過去に材料がresourceとして記録されていても、質問生成は現在の定義に従います。生成できない場合の質問例も、材料を誘いやすい「何を使ったか」から必要な知識を尋ねる形にします。作業に役立てる実践的な経験と、考え方・価値観が形成された背景としての `sources` は、本人が説明したつながりに沿って区別します。保存済みの状態や過去のスコアの一括再計算は行いません。

`state.deep_dive` に深掘りの対象・段階・元の業務を保持し、次の流れで進めます。

1. 対象が曖昧なときだけ `clarify`: 「他の優先すべきタスクは何ですか？」など、理由を聞く前提を一問で確認します。`deep_dive_needs_clarification` が false なら、この段階を省略します。
2. `reason`: 「それを優先するのは、どういった理由からですか？」など、理由・必要性・判断の手掛かりを一問だけ尋ねます。確認への回答で既に理由が語られた場合（`deep_dive_reason_answered`）は省略します。
3. 回答を受けたらanchorモードを解除し、元の業務についてcoverage・depthに応じた通常の方針へ戻します。同じ回答の別の語句で新たなanchorを開始しません。coverage達成済みでdepthが不足していれば、その業務についてまだ得られていない深さへ質問を続けます。

深掘りの途中で別タスクが挙がっても、面談の対象業務は切り替えません。終了意思、明確な抵抗、相手からの質問を優先し、その場合はanchorを解除します。`signs_of_no_information` は判定・方針選択に使いません。摩擦や訂正は短い謝罪と理解の修正を加えたうえで、通常の質問方針を続けます。通常のスコアによる終了は、anchorの質問への回答を受けてから判定します。LLM をモックしたテストは段階の遷移を確認しますが、表現の検出や生成質問の自然さは実際のモデルでの確認が必要です。

## 要約・記憶生成の失敗と再試行

終了時は会話本文と発話抜粋を先に保存します。要約のJSON解析や保存に失敗した場合は `session_memory_jobs.status=fallback` とし、発話抜粋を引き続き参照できます。成功した要約・プロフィール・構造化記憶は同じトランザクションで保存します。

`db/config.yaml` の `memory.recovery_enabled` で、起動時の復旧と稼働中の自動再試行の両方を切り替えます。現在は `false` として停止しており、再起動しても自動では再開しません。通常の面談終了時の初回の要約生成はこの設定の対象外です。`true` にして起動した場合は、起動時の復旧に加えて、稼働中も `run_memory_recovery` が失敗・未完了の処理を確認します。既定は60秒ごとに確認し、最後の試行から300秒以上経過した処理を古い順に1件ずつ再試行します（`db/config.yaml` の `retry_poll_seconds`・`retry_delay_seconds`・`retry_batch_size`）。失敗した要約の再試行中も `fallback` のままとし、次の面談の開始を妨げません。同一セッションの処理はプロセス内で重複実行せず、成功済みの処理は再実行しません。失敗が続く場合も元の会話を保持して再試行を続けます。モデル未設定時は定期推論を行いません。

JSON生成は `llm/config.yaml` の `json_generation` を使用し、既定の出力上限は4096トークン、サンプリングなしです。通常の質問文は従来どおり2048トークンです。`LOCAL_LLM_MAX_NEW_TOKENS` は両方の上限を上書きし、JSONだけを変更するときは `LOCAL_LLM_JSON_MAX_NEW_TOKENS` を指定できます。再試行時は要約150字程度・ノードと関係を最大3件ずつに絞って、出力途中で切れる可能性を減らします。JSONエラーには解析位置と出力文字数を記録し、出力がトークン上限に達した場合も警告を出します。エラー内の出力抜粋は先頭400文字のため、ログが途中で終わっていることだけでは実際の応答が途中で切れたとは断定できません。
